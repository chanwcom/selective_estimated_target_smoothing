# CTC test-set results

`results.jsonl` -- one JSON object per (checkpoint, split), appended by
whoever runs a decode. Nothing is overwritten; a re-run just adds a line
and the later `utc` wins.

`table.md` -- the same data as a table, regenerated by `make_table.sh`.
Read this one first.

## Why these are CPU numbers

An earlier version of this file said CPU and GPU decoding disagree by about
0.74 %. **That claim was wrong and is retracted.** It came from a single
200-utterance probe that compared GPU bf16 against CPU fp32, so it measured
dtype, not device. Two RNN-T fp32 pairs decoded on both devices over the
full dev sets agree to five decimal places.

The convention here is still CPU, for two reasons that survive:

  - **fp32 throughout.** bf16 does move the number; the probe above is real
    evidence of that even though it was mislabelled. Every line in this
    directory is fp32.
  - **batch_size = 1.** At bs=1 the GPU's advantage is only 1.6x (0.370 vs
    0.854 s/utterance), and bs=1 is itself 2.03x faster than bs=8 on CPU
    because `padding="longest"` pads to the batch's longest utterance and
    LibriSpeech spans 1-35 s. CPU lanes are plentiful here; GPUs are not.

`EVAL_PROTOCOL.md` in the parent directory is the authoritative version of
all of this, including why batch size changes WER at all.

## How a line is produced

    python wav2vec2_inference.py --checkpoint_dir <ckpt> \
      --vocab_size 32 --test_split test-clean --device cpu

`wav2vec2_inference.py` is the repo's own tool. Do not reconstruct WER by
grepping training logs: the training loop's eval and this one differ in
split and in cap, and mixing them is how the 200-utterance figures got
into tables in the first place.

## Reading a tag

    ctc_<profile><steps>_<method>_a<alpha>_s<seed>
    ctc_100hwsd15000_LS_a0p05_s3

`profile` is 1hr / 10hr6000 / 100hwsd15000. `method` is baseline, LS
(textbook label smoothing) or FAS.

A method's name comes from the checkpoint directory's suffix AND its beta,
not from either alone -- this cost two wrong inventories to work out:

  ..._classspace                        alpha_mode=fixed, class space  -> LS
  ..._beta_1p0_classspace_fas_eps...    FAS at beta=1                  -> LS
  ..._beta_0p0_classspace_fas_eps...    FAS proper                     -> FAS
  ..._aws_eps...                        AWS

The second line is textbook LS because apply_floored_active_support_
smoothing's beta=1 end is exactly (1-alpha)y + alpha/K, bit for bit; its
docstring says so and shc_loss_util_test.py checks it.
